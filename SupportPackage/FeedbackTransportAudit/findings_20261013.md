the server's Nagle algorithm or the client's delayed ACK policy.

Raw evidence is in `source_baseline.csv/.json` and

after subscription. Neither sent motion commands or registered publishers.
Endpoint was tested only after confirming no Unity connection to port 10000.

`baseline_path_comparison` matches 1,136 identical ROS timestamps. The Endpoint
probe's complete-read time was later than the direct probe by median 0.01425 s,
p95 0.02512 s, maximum 0.06857 s. The comparison tool labels its second input
`unity`, but **in this baseline only that input is the Python Endpoint probe,
not Unity**. Unmatched records were outside the common source-stamp span.

These results exclude a persistent 32 Hz limit in the source or Endpoint under
these conditions. They do not exclude a load-dependent problem during Unity XR.
The current PC wireless interface reported 2.4 GHz channel 10 (287 Mbps link
rate). This is a suspect shared resource, not proof of saturation.

## Semantic map isolation

The saved MainScene contains:

- `mINIMAP`: LivoscanWristMinimap enabled.
- `GameObject`: LivoscanDataSource enabled, server port 8770 on the Jetson.
- `livoscan`: full-size LivoscanWorldClient already disabled.

The X toggle only deactivates the minimap's visual children. It does not stop
the shared HTTP/WebSocket source. DataSource currently cancels its receive loop
in OnDestroy, not OnDisable, so disabling it after Start is not a reliable
network-off test. Exit Play, disable the minimap and DataSource before the next
Play, and keep the full-size view disabled. Otherwise a still-enabled view can
find or create a source. KAT/odometry control has no LivoscanDataSource dependency
in the current project.

If this improves performance, it implicates the module's additional workload;
it does not alone separate rendering, JSON processing, download traffic and
other shared resources. Keep other settings the same for the comparison.
