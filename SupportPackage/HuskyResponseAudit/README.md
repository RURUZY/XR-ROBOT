# Husky 底盘响应验收（人工切换控制源）

当前已提供控制链记录和导航故障暂停逻辑。没有新增仲裁器，没有改底盘轮径、轮距、反馈驱动或增加转向增益；尚无本轮实车响应结论。测试脚本只读本地文件，不能启动或驾驶机器人。

## 1. 每次实验准备

1. 手动只启用本次使用的一个控制源；先键盘底盘测试，再 KAT。切换前让车辆停止。机器人的其他控制源也由操作者关闭。
2. 保持前后指令上限 0.3 m/s、转向上限 0.5 rad/s。键盘脚本的速度参数也应核对；当前 KAT 限速不会替键盘限速。记录地面、载荷、电量、底盘参数、反馈来源、软件版本。
3. 外部固定录像拍清车身方向和地面距离标记；用已知直角/距离作独立测量。不要从 Unity 车身框或同一个里程计反过来验证自身准确性。
4. Windows Unity Editor 点 Play 自动采集。在 `KAT → 控制测试标记` 打开窗口，按试验编号添加 start、command_stop、end 等标签。菜单只是记录，不发送运动。记录机器人侧同一实验的 ROS bag（沿用现有 ROS 1 录制流程）。
5. 为外部录像与日志建立可识别的同步事件，记下偏移、误差范围并核对首尾漂移。标记窗口的点击时间不自动等于摄像机拍到的时刻；没测出时差就不要报告毫秒级物理延迟。
6. 一段 Play 中不改控制参数；换参数时结束该段并重新采集，避免一张响应表混用不同条件。

记录文件位于 `KATCaptures/KAT_MiniS_.../`，结束 Play 自动打包。新记录不会覆盖旧包。通过下列只读命令检查通道是否存在：

```powershell
python SupportPackage/HuskyResponseAudit/audit_capture.py "KATCaptures/KAT_MiniS_实际目录" --require-chassis
```

报告的 `required_channels_present` 只表示所需文件中有记录，不代表没有丢包、没有其他 ROS 发布者或车身运动准确。脚本另外检查事件次序、输入与请求/发布关联、写盘错误。完整性通过后仍要检查片段时间覆盖、bag 发布者和独立录像。

## 2. 分开看四层证据

| 层 | 文件/证据 | 能回答的问题 |
|---|---|---|
| 控制器读到的输入 | control_input / control_keyboard_input | 本次计算到底收到了什么 |
| 映射后的请求与 Unity 发布值 | control_request / control_publish | 朝向门控、限幅、限加速度改变了多少 |
| 底盘控制器输入/输出 | control_chassis_command，按 topic 区分；同次 ROS bag | 发到 ROS 的内容到达底盘控制器后是否不同 |
| 反馈与独立车身测量 | control_odometry + 外部固定录像/测量 | 里程计说移动了多少，实际移动了多少 |

`/husky_velocity_controller/cmd_vel_out` 是底盘控制器报告的速度输出，仍不是轮子执行或车身运动的独立证明。当前工程历史 bag 中它是 `TwistStamped`；输入是 `Twist`。现场话题不同或输出没有启用时，应先核对机器人现有配置；不能把缺记录当成零输出。

Unity 输入/请求/发布共用事件编号和接收时基。远端 ROS 消息保留源时间戳，可与 bag 的同一消息匹配；接收时间含网络延迟。Twist 输入没有源时间戳，不应凭“相同数值”声称精确匹配某一次发送。SDK 时间戳保持原值，没有确认其硬件时基。

## 3. 测试顺序及响应表

每个条件至少重复 3 次，左右与前后采用相同条件；每段从静止开始，结束后确认实际停稳。具体持续时间由可用场地决定，不自动执行固定时长动作。

| 试验 | 保持一致的条件 | 分开记录的结果 |
|---|---|---|
| 静止 | 零指令，记录约 10 秒 | 车身是否真静止、原始输入抖动、里程计漂移 |
| 直行、倒车 | 从较小指令逐级增大，最大不超过 0.3 m/s | 起动死区、延迟、稳态速度、偏航及前后差异 |
| 左转、右转 | 同幅度角速度指令逐级测试，最大不超过 0.5 rad/s | 起转死区、稳态转速、里程计与独立转角比例、左右差异 |
| 发零停止 | 从同一稳态速度发零 | 指令到零的时间、实际停稳时间、停止距离/余转角 |
| KAT 停步 | 相同踏步速度和步频 | 停步到零指令的尾部，与零指令后底盘惯性分别计算 |
| 换向 | 相同初始速度和反向目标 | 请求换向、底盘输出过零、车身实际反向三个时刻 |
| KAT 改目标 | 30°、90°，以及转到一半改变方向 | 目标是否实时改变、剩余方向误差、过冲、恢复行走行为 |

填写 `response-template.csv`，空项表示未测，不能填 0 代替未知。模板是待填写的试验记录，不含伪造实车数据。

- 死区：在相同场地上重复施加某幅度命令，独立测量是否持续出现运动；给出“未动的最高值/能动的最低值”区间。
- 延迟：明确起点是 KAT 输入、Unity 发布还是底盘输出，终点是独立测到车身起动；报告同步误差。不能混合命令延迟与里程计滤波延迟。
- 稳态：明确使用哪个稳定区间，计算独立位移/转角随时间的变化，再单独列出里程计估计。
- 停止距离：分别标记人停步、Unity 发零、底盘输出发零、车身停止，距离以独立测量为准。
- 左右不对称：比较相同幅度、地面、载荷下的多次结果，不用单次异常定增益。

先解释轮反馈、轮径及轮距/倍率配置和独立测量之间的差异，再决定是否调整转向增益。没有完成这些测量前，不宣称某个倍率可以修正实车误差。

## 4. 两种映射的比较与异常恢复

比较 `AccumulatedTurns` 与 `CurrentDirection` 时，固定速度上限、滤波、朝向减速和制动设置，只改变目标角的语义。累计模式本来也接受最新身体输入；两者主要区别是是否要求补齐累计多圈。若同时关闭辅助或恢复历史高限速，则是另一组实验，不能把结果只归因于映射。

当前导航配置：反馈过期立即停止相关运动输出；短暂中断保留待转目标；身体/里程计长中断、里程计参考重置、长期无转动进展要求松开再按扳机。重新激活建立新参考，不补做故障前的脚步。当前累计模式且辅助关闭仍保留历史自动恢复策略，仅作为明确选择的历史对照。

## 5. 视频验证仍需现场完成

顺序为车静止只转头、头保持不动只转车、组合运动。F6 进入标定预览暂停 Unity 球体朝向补偿，但不会停止机器人；先用原控制方式停住车辆。用真实视频中的门/墙面观察，不用车身框作为标准。根据原视频是否保持世界朝向选择模式，再停稳、对齐真实车头方向、F7 保存。

`videoHeadingDelaySeconds` 只是手动近似时差补偿，未获得逐帧视频采集时间戳；不自动估计相机稳定模式，不自动验证独立转角。此次未改变现有 Custom 模式，也未改底盘/视频标定参数。
