## 改了什么

- 前进保留 Direct 的 `sqrt(moveSpeed.x² + moveSpeed.z²)`、Mini S/C2 踏步信号、速度脉冲补偿和倒退模式。
- `forwardAttackTime=0`、`forwardReleaseTime=0`：默认不对前进输入做低通。`walkDeadZone=0.02` 保留以避免噪声启动。
- `stepPulseHoldTime` 从 Direct 的 0.60 秒缩短至 0.15 秒；设备踏步信号保持为 0.10 秒。保持时间不是低通时间，慢踏步可能出现间歇；可按日志调到 0.20～0.30 秒，而不是直接拉长全部输入滤波。
- 短暂起步/停止越过固定 20 Hz 发包间隔立即发送，避免一步在两个发包时刻之间被漏掉。
- 转向角度轻度滤波 0.04 秒，第二级速率滤波默认关闭。身体转速产生即时前馈，身体累计转角与机器人累计转角的误差产生反馈修正；目标比例固定为 1:1，行走状态不改变它。
- 速率死区只影响前馈，慢转的小角度仍完整累计。停止转身后保留目标，允许机器人补齐误差。
- 沿用 Direct/SDK 示例的连接状态与数据有效性检查，不再假设 `lastUpdateTimePoint` 是持续心跳。它仍记录在日志中。若 SDK 错误地保持 connected 并重复旧数据，本版不能靠这个时间戳检测出来。
- `/odometry/filtered` 缺失、超时、重复源时间戳或姿态跳变会使转向停用，需要主动重新对齐；前进通道独立运行。没有新鲜反馈就不能保证角度对应。

## 手动挂载

退出 Play。保留场景里的控制器作为参考，但禁用 `KatHuskyDirectController`、`KatHuskyHeadingFollowController` 和键盘 `CmdVelPublisher` 的组件启用框。把新脚本挂到 `katmanager`，同一时刻只使用一个 `/cmd_vel` 发布器。

新版沿用 Direct：内部 `Enable Robot Control` 默认开启，`Start Activated` 默认关闭；右扳机明确启动后才运动。没有 HeadingFollow 的 `Enable Linear Motion` 额外开关。若只观察传感器，关闭内部 `Enable Robot Control`。

`KatStatusHud` 新增 `Angle Controller` 槽位，能自动寻找新版组件，也可手动拖入。旧 `Controller` 槽仍给 Direct 使用；不要把新版拖进旧槽。新版启用时显示实际角度、目标角度、误差及转向停用原因。需要启用 HUD 组件才显示。

## 操作

| 按键 | 行为 |
|---|---|
| 右扳机 / 可选 T | 开始、暂停；每次重新开始建立新的身体与机器人方向参考 |
| 右主按钮 / 可选 E | 软件停止；解除后需重新开始 |
| 右次按钮 / 可选 R | 前进、倒退模式切换；不反转身体转向对应关系 |
| 左次按钮 / 可选 C | 暂停以重新对齐；下一次开始采用当前方向 |

默认 `Activation Latch=true` 为按一下切换。需要按住才运行可设为 false。键盘需开启 `Enable Keyboard Fallback` 并保持 Game 窗口焦点。下机前暂停：本版没有人体离开 KAT 的检测能力；机器人端仍需命令超时停车。

## 2026-09-13：连续 360° 转向修正

实机日志约 t=37.6 秒：`BodyTurn=127`、`Target=-208`、`Robot=-85.3`，约 123° 的滞后触发了原来的 120° 误差保护，转向随后进入 `EXCESSIVE ANGLE ERROR / REALIGN`。这是没能继续累计并完成一圈的直接原因。此前 800° 测试让机器人同步跟随，没有覆盖人转得更快、机器人积压超过 120° 的场景。

现在 `maxHeadingErrorDeg` 只限制比例反馈使用的误差，不再截断目标或取消校准。完整累计转角保持，限速仍为 `maxAngularSpeed`；超过 120° 显示 `CATCHING UP / TARGET PRESERVED`。新增实际转动进展检查：持续非小幅转向指令（绝对值至少 0.05 rad/s）在默认 5 秒内没有沿指令方向至少 1° 的里程计进展，则暂停转向并要求重新对齐。传感器断开、姿态跳变和里程计失效的原有检查保留。

HUD 同时显示人的累计转角和机器人的累计转角，避免把朝向归零（360° 等价于 0°）误认为没转；未校准时误差显示无效，不再误报零误差。

回归测试扩充至 26 项，通过：包含实测 123° 滞后复现、两个方向先转满 360° 再由限速机器人追上、卡住/反向运动的进展检测、暂停取消待完成转角。实际满圈效果尚需复测。0.5 rad/s 约为 28.6°/s，机器人转满一圈至少约 12.6 秒，减速收敛还需额外时间；1:1 指累计目标角度，不是瞬时同步或零误差。

## 2026-09-13 第二轮：修转向漂移、修 360° 不跟随

用户反馈两件事：转弯角度对不上、有点飘；以及原地转 360° 时 husky 基本不跟着转。下面按"证据 → 改动"记录，没实机验证的地方都标出来了。

### 用实测 bag 量出来的硬事实

`SupportPackage/husky_all_2026-09-11-00-09-19.bag`（键盘遥控那次）里，持续发 `angular.z` 的四段稳态命令对应的 `/odometry/filtered` 实际偏航速率：

| 命令 angular.z | 同时的 linear.x | 持续 | 实测偏航速率 | 实测/命令 |
|---|---|---|---|---|
| -0.60 | +0.40 | 4.7 s | -0.281 rad/s | 0.47 |
| +0.60 | +0.40 | 5.1 s | +0.273 rad/s | 0.45 |
| -0.60 | -0.40 | 10.7 s | -0.253 rad/s | 0.42 |
| +0.60 | -0.40 | 8.8 s | +0.246 rad/s | 0.41 |

即**这台车实际只转到命令值的 0.41~0.47 倍**，四段方向/前后都一致。原来 `maxAngularSpeed=0.5` 意味着实际上限只有约 0.22 rad/s ≈ **12.7°/s**，转满 360° 需要约 28 秒。人原地转一圈大概 2~3 秒，所以"360° 时车没跟着转"首先不是逻辑丢角度，而是物理上根本追不上，误差累积到几百度、看起来就像没动。

⚠️ 未解释的交叉验证：同一段左/右转里用轮编码器行程反推（轮径 0.1651 m、轮距 0.555 m，再乘 Clearpath 默认 `wheel_separation_multiplier=1.875`）得到约 ±180°，而 `/odometry/filtered` 和轮式 `odom` 都只报 ±85~89°。差了约 2 倍。要么是真实打滑很大，要么里程计偏航本身有标定问题。**这一条直接影响"1:1"的含义**：本控制器是拿 `/odometry/filtered` 做反馈的，所以它保证的是"角度和里程计认为的偏航 1:1"，如果里程计偏航本身缩放不对，误差归零时车身实际转的角度仍然不是 1:1。要判定这件事必须用外部固定机位拍一次已知角度（比如地面画 90°），不能在 Unity 这一侧解决。

### 代码问题与改动

1. **转向上限太低**（上表）。`maxAngularSpeed` 默认 0.5 → 1.0，并新增 `angularCommandScale=2`，把"想要的角速度"换算成"这台车真能转出来的 cmd_vel 值"（两个前馈/反馈项都乘它，`maxAngularSpeed` 仍然是最后的硬钳位）。人以 30°/s 转身时命令约 1.05 rad/s、实际约 27°/s，基本 1:1；转得更快就会饱和并累积滞后，之后补齐。
2. **任何瞬态都会把转向通道永久锁死**（"飘"和"360 不跟随"的主因之一）。原来里程计过期 >0.5 s、EKF/frame 跳变、body yaw 跳变、姿态无效，全都走 `InvalidateHeading` 并置 `turnNeedsRealign=true`，而自动标定的条件是 `!turnNeedsRealign`——只有手动按 C 或重新扣扳机才会解除。也就是说转圈中间掉一帧里程计，转向就停到本次会话结束，屏幕不看 HUD 根本不知道。现在改成自恢复：短暂中断（< `turnResyncGraceTime=1s`）把参考按同样的量平移，**待转角度原样保留**；中断超过 1 秒则把参考重新锚到机器人当前朝向（不执行来源不明的旧角度）。`turnNeedsRealign` 这个锁已删除，手动 C 键仍然可用。
3. **body yaw 跳变判据从"固定 45°/帧"改成速率判据**（`maxBodyYawRateDegPerSec=720`，以 45° 为下限）。原来快速转圈 + 一次掉帧就会产生合法的大步长（0.2 s × 300°/s = 60°）却被当成故障丢掉，直接丢角度；现在只有物理上不可能的（如日志里反复出现的 135~139°/帧 ≈ 6750°/s）才跳过，而且**只跳过这一个采样、不再停用整个通道**。若跳变持续超过 1 秒（说明读数真的偏过去了），才采用新基准并重新锚定，避免静默冻结。
4. **求速率用的 dt 错了**。原来除 `Time.fixedDeltaTime`，但 KAT 是在 `FixedUpdate` 里轮询的，SDK 更新率和物理时钟无关，卡帧后还会连跑多个 tick。真实过了 0.2 s 的转动除以 0.02 s 会把速率放大十倍。现在用相邻有效采样之间的真实 `unscaledTime`，滤波、速率、跳变判据统一用它。
5. **踏步时的滤波确实是"飘"的一个来源，用户的猜测方向是对的，但位置在转向通道而不是前进通道。** 原来 `bodyYawFilterTime=0.04s`（50 Hz 下时间常数只有 2 个 tick）对整度量化的原始角度做微分：一个 1° 的量化跳变就产生约 20°/s、2° 产生约 39°/s，而速率死区只有 6°/s，于是 `feedforward = rate×Deg2Rad×1` 能到 0.34~0.5 rad/s——单个量化抖动就能吃掉 70%~100% 的角速度上限，左右交替。踏步时髋部/腰环本身每步还会摆几度。改动：`bodyYawFilterTime` 0.04 → **0.18**、速率死区 6 → **10°/s**，新增 `stepTurnFilterMultiplier=2`（踏步信号有效期间时间常数再乘 2）。一阶低通作用在**累积角**上只产生滞后、不损失总角度，所以转完之后目标角仍然精确。
6. **目标角改用滤波后的累积角**（`DesiredRobotYawDeg` 用 `filteredBodyTurnDeg`）。之前目标直接跟原始累积角，量化和步态摆动会整条灌进设定值，反馈项跟着抖。
7. **小误差修不动**。`headingKp=0.8` 下 5° 误差只发 0.07 rad/s，按 0.45 倍折算实际约 0.03 rad/s，履带式车这种量级根本不动——误差就一直挂着，表现就是航向慢慢和人错开。新增 `minTurnCommand=0.25`（配 `minTurnCommandErrorDeg=5` 的迟滞和 `minTurnCommandHoldTime=0.2s` 的符号保持），只在误差确实超过 5° 且方向稳定时才抬到能破静摩擦的量，回到 `headingToleranceDeg=2°` 以内才释放，不会被步态摆动抖起来；也不会反向压制操作者正在进行的转身前馈。
8. **原地转身时踏步被当成走路**（"转身时飘"的另一个直接来源）。在跑步机上转 360° 必然要挪脚，`moveSpeed` 脉冲回退和设备踏步信号都分辨不出来，于是 `stepInPlaceInput=0.35` 合成出前进意图，车一边转一边以约 0.25 m/s 往前跑——画的是弧线不是原地旋转。新增 `stepDriveTurnSuppressionDegPerSec=25`：身体转速超过该值时只屏蔽**合成的**踏步前进量，真实 `moveSpeed` 幅值照常驱动前进，所以"边走边转"不受影响。设 0 可关掉这一耦合。
9. **`turnProgressTimeout` 触发后不再要求手动重对齐**，改为丢弃这次追不上的目标（`ReanchorTurnTarget`）。车被挡住时停止推，不会一直空转，也不需要人工介入才恢复。
